## Структура проекта

- `app/` — сервер, работа с LLM и симулятором, расчёт сценария.
- `app/static/` — страница интерфейса.

- `tests/` — локальные тесты с имитацией внешних сервисов.

## Локальный запуск первого прототипа

Нужны Python 3.11, доступ к API хакатона и выданный команде файл `api.token`. Значения токенов остаются вне репозитория.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
$env:HACK_API_URL = 'https://hack-api.be-healthy.tech'
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

В другом окне PowerShell, с активированным окружением, задайте переменные и создайте dev-прогон. Путь к токену укажите из выданного набора.

```powershell
$env:HACK_API_URL = 'https://hack-api.be-healthy.tech'
$env:HACK_TEAM_TOKEN = (Get-Content -Raw '<путь к api.token>').Trim()
python -m tools.dev_run
```

После обработки откройте `http://127.0.0.1:8000`. `tools/dev_run.py` создаёт dev-прогон через `/runs`, передаёт его токен в локальный `/run` и выводит число обработанных записей. При повторном запуске создаётся новый прогон, к которому могут применяться ограничения организаторов.

Приложение использует LLM для интерпретации просьб и извлечения предпочтений из профиля и истории. Демонстрационный сеанс создаётся отдельно от зачётного `/run` и использует командный токен только на сервере.

Для проверок выполните `python -m unittest discover -s tests -v`. Эти тесты используют имитацию API и не заменяют проверку на реальном стенде.



## Запуск через Docker

Нужны Docker Engine с Compose или Docker Desktop, а также доступ к API хакатона. Файл `api.token` должен находиться на компьютере вне репозитория. В Docker Desktop должен быть запущен Linux-контейнерный движок.

Из корня репозитория создайте локальную конфигурацию и выберите LLM. По умолчанию пример использует прокси организаторов:

```bash
cp .env.example .env
export LLM_API_KEY="$(tr -d '\r\n' < '/путь/к/llm.key')"
docker compose up -d --build
```

Для Google измените в `.env` строку на `LLM_PROVIDER=google` и перед запуском задайте `GEMINI_API_KEY`. Доступность Google-прокси зависит от сети. Ключи не должны попадать в Git.

Откройте http://localhost:8000. Сначала экран ожидает заезд. Проверьте работоспособность сервера командой `docker compose ps` или откройте http://localhost:8000/health.

Чтобы загрузить dev-набор и подготовить номер, в Linux, macOS или WSL выполните:

```bash
export HACK_TEAM_TOKEN="$(tr -d '\r\n' < '/путь/к/api.token')"
docker compose exec -e HACK_TEAM_TOKEN app python -m tools.dev_run --evaluate
unset HACK_TEAM_TOKEN
```

В PowerShell используйте:

```powershell
$env:HACK_TEAM_TOKEN = (Get-Content -Raw '<путь к api.token>').Trim()
docker compose exec -e HACK_TEAM_TOKEN app python -m tools.dev_run --evaluate
Remove-Item Env:HACK_TEAM_TOKEN
```

Команда с `--evaluate` создаёт dev-прогон, проверяет формат через `validate` и сравнивает состояние комнат после просьб с dev-эталоном. Она также приблизительно проверяет правила сна R1–R8; медицинские тексты и официальную итоговую оценку она не проверяет. Эта проверка вызывает выбранную LLM и расходует её лимит.

Для интерактивной демонстрации перед `docker compose up -d` задайте в терминале `HACK_TEAM_TOKEN` из `api.token`, чтобы Compose передал его серверу. На стенде токен предоставляет организатор. Откройте страницу и нажмите «Подготовить номер»: сервер создаст отдельный dev-прогон и сеанс, не вызывая LLM. Сценарий демонстрации использует данные профиля и заметок; отдельного извлечения предпочтений моделью при подготовке нет. Выберите виртуальное время номера и нажмите «Показать». Просьбы в чате обращаются к выбранной LLM. По истечении срока dev-прогона (45 минут) при следующем обращении создаётся новый; состояние и история демонстрации сбрасываются. После перезапуска сервера номер также нужно подготовить заново. Не размещайте командный токен во фронтенде или Git.

Адрес API по умолчанию — `https://hack-api.be-healthy.tech`. При необходимости задайте переменную `HACK_API_URL` перед запуском `docker compose up -d`. Для другого порта на компьютере задайте `APP_PORT`, например `APP_PORT=8080 docker compose up -d`, затем откройте http://localhost:8080. Контейнер привязан к localhost компьютера, на котором запущен Docker.

Для просмотра логов выполните `docker compose logs -f app`. Остановить приложение можно командой `docker compose down`. Настройка Docker предназначена для локального запуска, стенд организаторов разворачивает бэкенд по своему контракту.

## Настройка LLM

Для локального запуска через Google AI Studio задайте переменные окружения перед запуском Docker Compose:

```bash
export LLM_PROVIDER=google
export GEMINI_API_KEY='<ключ Google AI Studio>'
export GEMINI_MODEL='gemini-3.5-flash-lite'
docker compose up -d --build
```

В PowerShell используйте `$env:LLM_PROVIDER`, `$env:GEMINI_API_KEY` и `$env:GEMINI_MODEL` вместо `export`. Значение ключа остаётся вне кода и Git. Идентификатор модели можно заменить на доступный вашему ключу. После изменения переменных пересоздайте контейнер командой `docker compose up -d`.

Для локального запуска Python задайте те же переменные в окне сервера перед запуском uvicorn. Без настроенного ключа обработка набора и чат не работают.

На стенде хакатона используйте только прокси организаторов. Прямой Google API и личные ключи условиями кейса не разрешены. Сервер автоматически выберет прокси, когда задан `LLM_BASE_URL` и не задан `LLM_PROVIDER`. Для Compose укажите `LLM_PROVIDER=sain` и переменные `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`. Текст запросов и заметок передаётся выбранному провайдеру.

По умолчанию запросы к Gemini идут через прокси `https://gemini-proxy.ilyuxa-chernov-04.workers.dev`. Он получает заголовок с ключом и пересылает запрос в Gemini API. Другой HTTPS-адрес можно указать переменной `GEMINI_BASE_URL`. API хакатона использует `HACK_API_URL`.

## Подключение провайдера и ограничения

В `.env` переключайте `LLM_PROVIDER=sain` или `LLM_PROVIDER=google`. Перед пересозданием контейнера задайте в том же терминале ключ выбранного провайдера в `LLM_API_KEY` или `GEMINI_API_KEY`. Для интерактивного номера также задайте `HACK_TEAM_TOKEN` перед запуском Compose. Чтобы применить конфигурацию, выполните `docker compose up -d --force-recreate`.

Стенд запускает `start.sh` и передаёт `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`. Без явного `LLM_PROVIDER` приложение выбирает прокси организаторов при наличии `LLM_BASE_URL`. Параметры стенда управляются организаторами. Собственный ключ Google используется только при локальной разработке.

Для прокси организаторов приложение ограничивает частоту исходящих вызовов в своём процессе и повторяет ответы 429/5xx с задержками 5, 10 и 20 секунд. Этот лимит общий для всей команды, поэтому другие процессы тоже расходуют квоту. После успешного прогона в логе записываются агрегированные `calls`, `input_tokens`, `output_tokens`, `total_tokens` и `missing_usage`, если провайдер передал сведения об использовании. Для онлайн-набора фактическая стоимость в токенах ещё не измерена. Суточная квота общая для разработки и проверки.

## Журнал технических решений

- Обработку естественного языка и извлечение предпочтений передали LLM. Настройки устройств проверяются кодом по диапазонам и каталогу.
- Используем сеанс симулятора отдельно для каждого заезда и просьбы. История реплик хранится отдельно по пользователю.
- При некорректной команде модели повторяем запрос до трёх раз. После трёх некорректных ответов возвращаем отказ по этой просьбе.
- Для dev-проверки добавлена локальная сверка итоговых состояний и классов ответа с открытым эталоном. Добавлена приблизительная проверка R1–R8; медицинские формулировки и официальная итоговая оценка не проверяются.
- Время отбоя переводится из домашнего часового пояса в пояс отеля. При разнице от трёх часов применяется сдвиг в сторону местного времени.

## Результаты и ограничения проверок

- До сокращения истории полный dev-прогон через прокси организаторов обработал 5 заездов и 38 просьб, прошёл `validate` и совпал с открытым эталоном по 20 из 38 просьб; расход составил 225 026 токенов. Эти результаты относятся к предыдущей версии.
- После сокращения истории и исправления обработки объединённых реплик локальный dev-прогон через Google прошёл `validate` и совпал с эталоном по 23 из 38 просьб; расход составил 75 193 токена. Результат относится к предыдущей версии и не является результатом модели организаторов.
- После уточнения инструкций модели локальный dev-прогон через Google обработал 5 заездов и 38 просьб, прошёл `validate`, совпал с эталоном по 29 из 38 просьб и прошёл приблизительную проверку R1–R8 для пяти заездов. Расход — 87 154 токена, пик памяти — около 55 МБ при лимите 512 МБ. Результат не является оценкой модели организаторов.
- Полный прогон итоговой версии через прокси организаторов не завершился: сервис вернул HTTP 429, указав исчерпание общей суточной квоты команды. Качество итоговой версии с этой моделью пока не измерено. Квота общая для разработки и официальной проверки; время её сброса сервис не сообщил.
- Для сокращения расхода модель получает отобранные по ключевым словам исторические записи и краткую память; важная информация, выраженная другими словами, может быть пропущена.

В ходе разработки отказались от повторной передачи всей истории на каждую просьбу из-за расхода токенов и от отдельных ответов на реплики внутри одной просьбы после сверки с dev-эталоном. Успешный `validate` подтверждает формат результата, но не качество управления номером.
